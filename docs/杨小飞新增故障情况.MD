# 杨小飞新增故障情况

本文总结新增的五个“连接与会话管理”故障 Case、各模式模拟的故障场景，以及 DBChaos 实际采用的注入方式。

## 故障 Case 总览

| 故障 Case | 模拟的数据库故障场景 | 实际注入方式 |
| --- | --- | --- |
| 空闲会话积压 | 大量客户端连接已经建立，但长时间没有执行 SQL，导致数据库连接、线程或进程以及会话内存被持续占用；可模拟连接池泄漏、应用忘记归还连接、连接清理滞后等问题。 | DBChaos 使用真实数据库账号建立多个 JDBC 连接，连接成功后不执行用户业务 SQL，只保持连接打开并处于空闲状态，持续一段时间后再关闭。 |
| 空闲事务积压 | 客户端开启了事务并访问过数据，但事务迟迟没有提交或回滚，导致事务状态长期存在；可模拟请求结束后忘记结束事务、事务清理延迟、长事务影响资源回收等问题。 | DBChaos 建立 JDBC 连接，执行 `BEGIN`，读取实验表中的一行数据，然后保持事务和连接打开，不执行 `COMMIT` 或 `ROLLBACK`，直到注入窗口结束后清理连接并回滚。 |
| 会话强制终止 | 数据库管理员误杀会话、节点重启、故障切换或服务端主动清理导致已有会话突然断开；用于观察数据库终止会话和释放资源的行为。 | DBChaos 先建立一批正常目标会话并取得每个会话 ID，再使用独立控制连接调用数据库的会话终止操作：PostgreSQL/openGauss 使用 `pg_terminate_backend`，MySQL/MariaDB 使用 `KILL CONNECTION`。该 Case 不实现应用或连接池重连。 |
| 连接认证失败 | 应用使用错误用户名、错误密码或失效凭据连接数据库，导致认证阶段被拒绝；也可模拟错误配置发布或短时间错误登录请求突增。 | DBChaos 每次运行生成一个不存在的临时用户名，使用当前数据库 URL 和密码发起连接。连接在认证阶段被数据库拒绝，不创建新用户，不修改真实账号，也不执行 SQL。 |
| 连接握手停滞 | TCP 连接已经到达数据库端口，但客户端协议初始化没有完成；可模拟客户端在建连后卡死、握手报文发送不完整或网络中断留下未完成握手连接。 | DBChaos 使用原始 TCP Socket 建连，不通过 JDBC 完成握手；按模式不发送协议报文或只发送固定协议前缀，然后保持连接到观察窗口结束。MySQL `partial` 会先读取服务器问候再发送客户端响应前缀。该 Case 不认证、不发密码、不执行 SQL。 |

## 各 Case 的模式

| 故障 Case | 模式 | 具体模拟场景 | 实现行为 |
| --- | --- | --- | --- |
| 空闲会话积压 | `fixed` | 一次性出现固定规模的连接池泄漏或连接未归还。 | 建立固定数量的连接，并保持它们全部空闲。 |
| 空闲会话积压 | `ramp` | 应用持续接收请求并建立新连接，但连接释放速度跟不上建立速度。 | 空闲连接数量按阶段逐步增加。 |
| 空闲会话积压 | `random_hold` | 不同请求、租户或连接池连接的占用时间不一致。 | 每个连接保持随机时长后释放，连接数量会随机增加和减少。 |
| 空闲事务积压 | `fixed` | 一批请求同时忘记提交或回滚事务。 | 固定数量的只读事务读取实验表后全部保持打开。 |
| 空闲事务积压 | `ramp` | 应用持续开启事务，但事务结束速度低于开启速度。 | 空闲事务数量逐步增加。 |
| 空闲事务积压 | `random_hold` | 不同事务因业务耗时或清理延迟而保持不同时间。 | 每个事务随机保持一段时间后释放，未结束事务数量随时间变化。 |
| 会话强制终止 | `serial` | 会话陆续被管理员清理、网络连接陆续断开或服务端逐个回收。 | 先建立目标会话，再逐个终止，每次终止之间等待 `interval`。 |
| 会话强制终止 | `burst` | 数据库重启、故障切换或网络异常造成大量会话同时断开。 | 先建立目标会话，再通过有限并发批量终止。 |
| 连接认证失败 | `serial` | 错误凭据持续、低频地出现。 | 按 `interval` 间隔逐个使用虚构用户名发起认证。 |
| 连接认证失败 | `burst` | 配置错误发布、凭据整体失效或异常登录流量造成认证失败峰值。 | 使用有限并发，在短时间内发起大量认证尝试。 |
| 连接握手停滞 | `silent` | 客户端与数据库建立 TCP 连接后，客户端进程卡住或未能发送协议启动报文。 | 建立 TCP Socket 后不发送数据库协议数据，并在设定的观察时长内保持连接。 |
| 连接握手停滞 | `partial` | 客户端只发送部分握手数据后卡住或连接中断，服务端持续等待剩余报文。 | PostgreSQL 发送协议 3.0 启动包前 12 字节；openGauss 7.0.0-RC2 发送协议 3.51 启动包前 12 字节；MySQL/MariaDB 读取服务器问候后只发送客户端响应前 8 字节，然后保持连接。 |

## 需要区分的概念

- **空闲会话积压**保持的是已认证的连接，但没有事务。
- **空闲事务积压**保持的是已认证连接中的未结束事务，事务已经访问过实验表。
- **会话强制终止**测试的是数据库服务端终止已有会话后的行为，不会自动模拟应用重连。
- **连接认证失败**测试的是认证阶段拒绝，不等同于连接数达到上限，也不等同于连接建立后再被断开。
- **连接握手停滞**停留在数据库协议握手阶段，和已经进入认证阶段并收到认证拒绝的连接不同；数据库对端 EOF 不能单独证明发生了超时回收，需要结合服务端日志判断。

这些注入都由 DBChaos 自身建立连接、执行控制操作或发起认证请求完成，不需要修改业务表；空闲事务只读取专用实验表。

## 实验注入说明

### 运行前准备

五个 Case 均可通过 `--db postgresql`、`--db opengauss` 或 `--db mysql` 选择目标数据库。运行前确认 `config/db.properties` 中对应数据库的 URL、账号和密码已经配置，并在 classpath 中包含匹配的 JDBC 驱动。下面用 PostgreSQL 展示完整命令；改测 openGauss 或 MySQL 时，把 `--db` 和驱动 jar 分别改为 `opengauss` / `lib/opengauss-jdbc-7.0.0-RC2.jar` 或 `mysql` / `lib/mysql-connector-j-8.0.33.jar`。

```bash
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" \
  chaos.Main --db postgresql session <case> <参数>
```

`<case>` 和 `<参数>` 替换为下文对应的 Case 名及命令参数。示例会连接真实数据库并占用会话资源，请先确认目标地址、权限和测试时间窗口。不要把数据库密码直接写入命令行或提交到仓库。

### 空闲会话积压

**前置条件：**目标账号能够建立 JDBC 连接，数据库尚有足够的连接额度。此 Case 不执行 SQL。成功启动后，DBChaos 会在注入结束时关闭自己建立的连接。

| 参数 | 含义与取值 |
| --- | --- |
| `-mode` | `fixed`、`ramp`、`random_hold`，默认 `fixed`。 |
| `-count` | 目标连接数，必填，1–200 个。 |
| `-duration` | 注入窗口，必填，1–86,400,000 毫秒（最多 24 小时）；`ramp` 下还必须不小于 `count` 毫秒。 |
| `-min-hold` | 仅用于 `random_hold`，连接最短保持时间，1 毫秒至 `duration`；默认 `duration/2`。 |

```bash
# 固定数量保持空闲
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session idle_session_buildup -mode fixed -count 20 -duration 60000
# 逐步建立
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session idle_session_buildup -mode ramp -count 20 -duration 60000
# 随机保持后释放
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session idle_session_buildup -mode random_hold -count 20 -duration 60000 -min-hold 10000
```

**预期结果与影响：**数据库会话视图中可看到 DBChaos 新建的空闲连接；`fixed` 在窗口内基本保持目标数量，`ramp` 逐渐增加，`random_hold` 会有连接陆续减少。空闲连接一般不会持续消耗明显 CPU，但会占用连接槽、会话内存，以及数据库实现对应的线程或进程资源；实际影响取决于连接数、数据库配置和当前负载。注入结束后连接应被关闭。

### 空闲事务积压

**前置条件：**`-table` 指向目标库中已有、可读且至少含一行的实验表；MySQL/MariaDB 上该表必须使用 InnoDB。建议使用专用实验表，不要指定业务表。程序开始后先读取一行，再保持只读事务打开；结束时回滚并关闭连接。

| 参数 | 含义与取值 |
| --- | --- |
| `-mode` | `fixed`、`ramp`、`random_hold`，默认 `fixed`。 |
| `-table` | 必填，普通表名或 `schema.table`；名称只允许字母、数字、下划线和 `$`，且必须以字母或下划线开头。 |
| `-count` | 事务数，必填，1–50 个。 |
| `-duration` | 注入窗口，必填，1–600,000 毫秒（最多 10 分钟）。`ramp` 下还必须不小于 `count` 毫秒。 |
| `-min-hold` | 仅用于 `random_hold`，事务最短保持时间，1 毫秒至 `duration`；默认 `duration/2`。 |

```bash
# 一批只读事务保持打开
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session idle_transaction_buildup -table dbchaos_txn_demo -mode fixed -count 10 -duration 60000
# 事务逐渐累积
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session idle_transaction_buildup -table dbchaos_txn_demo -mode ramp -count 10 -duration 60000
# 随机时长后回滚释放
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session idle_transaction_buildup -table dbchaos_txn_demo -mode random_hold -count 10 -duration 60000 -min-hold 20000
```

**预期结果与影响：**活动事务视图中应出现已访问实验表、随后处于空闲状态的事务；模式决定事务数量保持、递增或逐步减少。等待阶段不持续执行 SQL，也不写业务数据。事务会保留连接和事务快照等资源；普通只读查询仍可能持有读锁或元数据锁，旧快照也可能延迟部分清理工作（例如 PostgreSQL 的 dead tuple 回收），具体取决于数据库引擎和并发写入。CPU 通常主要花在连接和初始化查询阶段，不能假定持续升高。

### 会话被强制终止

**前置条件：**DBChaos 先建立目标会话，再通过独立控制连接终止它们。PostgreSQL/openGauss 控制账号需具备终止其他会话的权限；MySQL 账号需有 `KILL` 权限。默认复用 `db.properties` 的账号，也可用 `-control-user`、`-control-password` 指定控制账号。不要在多人共用的终端中把密码作为命令参数输入。

| 参数 | 含义与取值 |
| --- | --- |
| `-mode` | `serial` 或 `burst`，默认 `serial`。 |
| `-count` | 目标会话数，1–100 个，默认 10。 |
| `-interval` | `serial` 模式下相邻终止尝试之间的间隔，0–60,000 毫秒，默认 500；目标会话也会按此间隔逐个建立。 |
| `-concurrency` | `burst` 模式下并发终止数，1–32 个，默认 `min(count, 10)`。 |
| `-control-user` | 控制连接用户名，默认使用配置账号。 |
| `-control-password` | 控制连接密码，默认使用配置密码。 |

```bash
# 逐个终止
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session session_forced_termination -mode serial -count 10 -interval 1000
# 并发批量终止
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session session_forced_termination -mode burst -count 20 -concurrency 10
```

**预期结果与影响：**目标连接先出现在数据库会话视图，随后逐个或成批消失；命令输出应报告目标建立数和终止成功/失败数。该 Case 不会创建应用重连。数据库需清理对应会话资源；若目标连接持有未提交事务，终止时数据库会回滚它。CPU 和日志活动可能短暂增加，通常随终止数量和事务回滚量变化；目标连接释放后，其会话资源应回收。

### 连接认证失败

**前置条件：**配置的 URL、网络和 JDBC 驱动必须能正常到达目标数据库，否则结果可能被统计为其他连接错误，而不是认证拒绝。DBChaos 每次运行生成不存在的用户名，不需要创建测试用户，也不会改动配置账号。

| 参数 | 含义与取值 |
| --- | --- |
| `-mode` | `serial` 或 `burst`，默认 `serial`。 |
| `-count` | 认证尝试次数，1–200 次，默认 20。 |
| `-interval` | `serial` 模式尝试间隔，0–60,000 毫秒，默认 500。 |
| `-concurrency` | `burst` 模式并发数，1–32，默认 `min(count, 10)`。 |
| `-login-timeout` | 单次 JDBC 登录超时，1–60 秒，默认 10 秒。 |

```bash
# 间隔发起认证失败
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session connection_auth_failure -mode serial -count 50 -interval 500 -login-timeout 10
# 并发发起认证失败
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session connection_auth_failure -mode burst -count 50 -concurrency 10 -login-timeout 10
```

**预期结果与影响：**命令输出中“认证拒绝”应大于零；“其他连接错误”应为零或能由网络、驱动、超时等原因解释。认证失败的连接不会作为已登录会话长期保留。数据库可能产生认证日志或审计记录，认证处理会带来短暂 CPU 和网络开销；高频失败可能增加日志量或触发数据库自身的安全策略，具体依配置而定。

### 连接握手停滞

**前置条件：**目标 JDBC URL 必须对应可达的单一主机、端口和数据库，且不得含查询参数、TLS、代理或多主机地址；如配置 URL 不符合该范围，可通过 `-url` 覆盖为直连地址。此 Case 使用原始 TCP Socket，不使用 JDBC 驱动完成认证。命令中的 JDBC 驱动仍由 `--db` 初始化配置时加载。

| 参数 | 含义与取值 |
| --- | --- |
| `-mode` | `silent` 或 `partial`，默认 `silent`。 |
| `-count` | 并发 TCP 连接数，1–200 个，默认 10。 |
| `-duration` | 每条连接进入停滞后的观察时长，1–3,600,000 毫秒，默认 60,000。 |
| `-connect-timeout` | TCP 建连超时，1–60,000 毫秒，默认 10,000；不包含系统 DNS 解析时间。 |
| `-greeting-timeout` | MySQL `partial` 模式读取完整服务器问候的超时，1–60,000 毫秒，默认 10,000。 |
| `-url` | 可选，覆盖配置 URL；仅支持单地址、无查询参数、非 TLS 直连 URL。 |

```bash
# 建立连接但静默等待
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session connection_handshake_stall -mode silent -count 50 -duration 30000 -connect-timeout 10000
# 发送协议前缀后停滞
java -cp "config:lib/postgresql-42.7.2.jar:target/DBChaos-0.0.1.jar" chaos.Main --db postgresql session connection_handshake_stall -mode partial -count 50 -duration 30000 -connect-timeout 10000
```

**预期结果与影响：**客户端输出应显示 TCP 建连数和进入停滞数；服务端是否将其显示为未认证连接、以及何时清理，取决于数据库协议实现和超时配置。`silent` 不发送数据库协议报文；`partial` 发送固定长度的协议前缀后停住。服务端可能暂时占用未认证连接槽、网络缓冲区和连接处理资源，客户端也占用 Socket/线程；大量连接可能增加内存和连接管理开销。该 Case 不发送密码、不执行 SQL；EOF 只说明对端关闭，不能单独证明数据库发生了超时回收。窗口结束后 DBChaos 会关闭仍持有的 Socket。

## 如何确认注入结果

优先结合 DBChaos 命令输出和数据库会话/事务视图观察：空闲会话看连接数及状态，空闲事务看事务状态及等待事件，会话强制终止看目标会话是否消失，认证失败看认证拒绝计数，握手停滞看未认证连接和 DBChaos 的逐连接结果。数据库日志、连接上限、认证策略、当前负载都会影响观测；不要仅凭 CPU 或内存曲线判定注入成功。所有数字参数的单位和范围以上表为准，超出范围时注入器会拒绝执行。
